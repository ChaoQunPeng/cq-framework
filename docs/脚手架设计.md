# 个人项目脚手架设计（v1）

## 一、设计目标

搭建一套属于自己的项目脚手架，能够根据项目需要自由组合技术栈，而不是每次重新搭建项目。

例如：

* Web（React / Vue）
* Electron
* NestJS
* SQLite
* MongoDB

所有能力都应该是**按需添加**，而不是默认全部集成。

例如：

```text
创建 React 项目
        ↓
需要 Electron
        ↓
添加 Electron

需要 SQLite
        ↓
添加 SQLite

需要远程接口
        ↓
添加 Server（NestJS）

需要 MongoDB
        ↓
添加 MongoDB
```

最终目标：

> **只关注业务开发，而不是重复搭建项目。**

# 三、目录职责

## apps

**所有可运行的应用。**

每一个目录都代表一个独立 Application。

例如：

```text
apps

├── diary
├── admin
├── website
└── server
```

每个应用拥有自己的：

* package.json
* src
* vite.config
* electron（可选）
* sqlite（可选）

例如：

```text
apps

└── diary
    ├── src
    ├── electron（可选）
    ├── sqlite（可选）
    └── package.json
```

以后可以不断新增应用：

```text
apps

├── diary
├── admin
├── cms
├── website
├── mobile
└── server
```

脚手架未来应该围绕 **Application** 工作。

例如：

```bash
create app diary --react

add electron diary

add sqlite diary

add tailwind diary
```

# domain

## 定义业务模型（Business Model）

domain 不是数据库。

不是 React。

不是 NestJS。

也不是 Electron。

它描述的是：

> **产品本身。**

例如：

```text
Diary
User
Role
Tag
Mood
Weather
```

这些东西，即使把：

* React
* Vue
* Electron
* NestJS
* SQLite
* MongoDB

全部删除，

它们依然存在。

因为它们属于产品，而不是技术。

例如：

```ts
export interface Diary {
    id: string;
    title: string;
    content: string;
    mood: Mood;
    status: DiaryStatus;
}
```

例如：

```ts
export enum DiaryStatus {
    Draft,
    Published,
    Archived
}
```

例如：

```ts
export interface User {
    id: string;
    nickname: string;
}
```

这些全部属于 Domain。

建议目录：

```text
domain

├── diary
│   ├── Diary.ts
│   ├── DiaryStatus.ts
│   ├── Mood.ts
│   └── Weather.ts
│
├── user
│   ├── User.ts
│   └── Role.ts
│
└── tag
    └── Tag.ts
```

---

## Domain 的作用

整个项目只有一份业务模型。

React：

```ts
import { Diary } from "domain"
```

Electron：

```ts
import { Diary } from "domain"
```

NestJS：

```ts
import { Diary } from "domain"
```

以后：

SQLite：

```ts
save(diary: Diary)
```

MongoDB：

```ts
save(diary: Diary)
```

全部共享同一个业务模型。

避免：

* React 一份
* Electron 一份
* NestJS 一份

导致重复维护。

---

## Domain 不应该放什么？

不要放：

React

```tsx
<DiaryCard />
```

不要放：

TypeORM

```ts
@Entity()
```

不要放：

Mongoose

```ts
new Schema()
```

不要放：

axios

```ts
request.get(...)
```

不要放任何框架实现。

Domain 只负责：

> **定义业务。**

# shared

## 公共能力

shared 与业务无关。

任何项目都可以使用。

例如：

```text
shared

├── utils
├── logger
├── constants
├── config
└── types
```

例如：

```ts
formatDate()

uuid()

sleep()

deepClone()
```

这些放 shared。

---

## shared 判断标准

问自己：

> **如果明天写一个外卖系统，这个东西还能继续使用吗？**

如果答案是：

可以。

那么：

放 shared。

例如：

```ts
formatDate()
```

可以。

放 shared。

例如：

```ts
DiaryStatus
```

不能。

因为它属于日记业务。

所以：

放 domain。

# 五、目前不加入的目录

## api-contract

暂时不加入。

原因：

目前项目可能：

React

↓

Electron

↓

SQLite

甚至没有 Server。

等以后：

多个应用需要共享：

* HTTP DTO
* IPC Contract
* WebSocket Message

再抽离也完全来得及。

遵循：

> **按需抽象，而不是提前设计。**

---

## packages

暂时不加入。

目前：

只有：

```text
domain
shared
```

没有必要再增加一层 packages。

以后如果共享模块越来越多，例如：

```text
ui
sdk
eslint-config
tsconfig
vite-config
tailwind-config
```

再统一迁移到：

```text
packages/
```

即可。

# 七、设计原则

## 1、按需增加能力

不要一开始集成所有东西。

例如：

Electron

SQLite

MongoDB

Redis

Docker

……

只有真正需要的时候才添加。

---

## 2、按需抽象

不要为了未来可能会用而增加目录。

只有：

多个应用开始复用。

才抽离：

* shared
* api-contract
* ui
* sdk

---

## 3、业务与技术分离

永远区分：

业务：

```text
Diary
User
Mood
Role
```

技术：

```text
React
Electron
NestJS
SQLite
MongoDB
```

业务属于：

```text
domain
```

技术属于：

```text
apps
```

---

## 4、共享的是业务，而不是实现

整个项目只有：

一份：

```ts
Diary
```

而不是：

React 一份。

NestJS 一份。

Electron 一份。

SQLite 一份。

这样可以保证整个项目始终围绕同一套业务模型开发。

---

# 八、一句话总结

> **apps 负责运行，domain 定义产品，shared 提供公共能力。整个脚手架遵循"按需组合、按需抽象、按需演进"的原则。**
